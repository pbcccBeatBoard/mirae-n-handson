분석 대상 폴더(`legacy/...`)의 파일은 **읽기만 한다.** 어떤 경우에도 수정하지 않는다.

## 0. 모듈명 정하기

`<모듈 경로>` 를 아래 표로 `<모듈명>` 으로 바꾼다. 출력 경로는 폴더 이름이 아니라 이 표의 `<모듈명>` 을 쓴다.

| 모듈 경로 | 모듈명 |
|---|---|
| `legacy/item-bank-php` | `item-bank` |
| `legacy/assignment-thymeleaf` | `assignment` |
| `legacy/grade-mssql` | `grade` |

## 1. 계획 먼저 제시

작업 시작 전 다음 4단계(진입점 → 의존 관계 → 데이터 흐름 → 비즈니스 규칙 후보)의 대상 파일 목록과 각 단계에서 만들 산출물을 요약해 사용자에게 먼저 보여주고 진행 확인을 받는다. 범위 제한 인자가 있으면 그 범위로 한정해 계획한다.

## 2. 진입점 분석 → `docs/<모듈명>/ARCHITECTURE.md`

- 모듈 개요, 폴더 구조, "URL/화면 → 처음 실행되는 파일 → 주요 함수 호출" 표를 만든다.
- 함수 호출은 함수명과 근거 파일:줄번호(정의 위치 + 호출 위치)를 같이 적는다.
- 확인하지 못한 부분은 "미확인 목록" 절에 남기고 추측으로 채우지 않는다.
- 작성이 끝나면 파일로 저장한 뒤에만 다음 단계로 넘어간다.

## 3. 의존 관계 분석 → `ARCHITECTURE.md`에 이어서 저장

- 모듈 내부 파일 간 호출 관계를 Mermaid `flowchart`로 그리고, "A → B" 호출 표(근거 파일:줄번호)를 덧붙인다.
- 외부 모듈/라이브러리 의존(예: `vendor/`)도 표시한다.
- 가장 긴 함수(또는 최상위 스크립트) 상위 3개와 하는 일을 표로 남긴다.
- 저장 후 다음 단계로 넘어간다.

## 4. 데이터 흐름 분석 → `docs/<모듈명>/ERD.md`

- 이 모듈 코드가 실제로 접근하는 테이블/뷰만 범위로 삼는다(스키마 전체를 다루지 않는다).
- 테이블 목록(주요 컬럼, 근거: 스키마 정의 파일:줄번호 + 코드 사용 위치)을 표로 만든다.
- 관계는 Mermaid `erDiagram`으로 그리고, FK 제약으로 **선언**된 관계와 코드의 JOIN/WHERE로만 **추정**되는 관계를 구분해 표시한다.
- 테이블별 읽기(SELECT)/쓰기(INSERT/UPDATE/DELETE) 위치 표를 만든다.
- 스코프 밖이라 다루지 않은 테이블, 확인 못한 부분은 "스코프 메모"/"미확인" 절에 남긴다.
- 저장 후 다음 단계로 넘어간다.

## 5. 비즈니스 규칙 후보 → `docs/<모듈명>/BUSINESS-RULES.md`

각 규칙은 반드시 아래 6개 필드를 이 순서로 적는다.

- ID (예: BR-01)
- 규칙: 한 문장으로, 조건과 결과를 명확히
- 근거: 파일:줄번호
- 근거 코드: 실제 코드 인용(블록)
- 확신도: 확실 / 추정 (추정이면 왜 추정인지 한 줄)
- 비고: 매직 넘버, 주석-코드 불일치, 관련 규칙 등(없으면 "없음")

코드에 없는 규칙은 쓰지 않는다. 근거가 주석뿐이고 이를 강제하는 코드가 없으면 규칙으로 올리지 않고 "코드가 아닌 주석에만 있는 항목" 절에 남긴다. 주석과 코드가 다르면 코드를 기준으로 규칙을 쓰고 주석 내용은 비고에 적는다. 매직 넘버는 문서 끝에 표로 모은다.

## 하지 말 것

먼저 대상 모듈의 기존 `docs/<모듈명>/BUSINESS-RULES.md`에 "검증 이력" 절이 있는지 확인한다.

- 있으면: 그 절에 기록된 실제 오류 유형을 다시 읽고, 같은 유형(예: 존재하지 않는 함수를 근거로 든 경우, 호출 방향을 반대로 적은 경우)을 이번 산출물에서 반복하지 않는다.
- 없으면(이전 표본 검증에서 전부 통과했거나 이번이 첫 실행인 경우): 다음을 특히 조심한다.
  - 코드에 실제로 정의되지 않은 함수 · 메서드를 근거로 드는 것
  - 호출 방향(A→B)을 실제와 반대로 적는 것
  - 코드에 없는 규칙을 "일반적으로 이렇게 할 것 같다"는 추측으로 창작하는 것

## 6. 사람이 표본 점검할 규칙 추천

`BUSINESS-RULES.md` 작성을 마친 뒤, 사람이 직접 코드를 열어 표본 검증하면 좋을 규칙 3개를 추천하며 마무리한다. 이 중 하나는 반드시 "가장 그럴듯해서 오히려 의심 없이 넘어가기 쉬운 규칙"으로 고른다. 추천마다 ID와 고른 이유를 한 줄로 적는다.
